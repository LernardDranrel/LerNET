# LerNET v1.1.0 — критерии приёмки

Источник требований: [утверждённый план](v1.1.0-network-manager.md) и [каталог экранов](../design/v1.1.0/index.html). Дата ревизии: 2 октября 2026. Эта страница фиксирует проверяемый результат; наличие кода или успешная компиляция не подтверждают сетевую гарантию.

## Порядок проверки

1. **Соответствие задаче:** каждый сценарий ниже выполняется на Android и Windows либо явно и правдиво отмечен как недоступный в пределах утверждённого плана. Основные требования общего TUN, независимых выходов и применения на ходу не заменяются отметкой «недоступно».
2. **Качество реализации:** проверяются реальные вызовы закреплённого ядра, границы модулей, конкуренция, отмена, владение ресурсами, миграция и обработка ошибок. Ошибки исправляются с повторной проверкой затронутого сценария.
3. **Приёмка сборок:** единая версия, сборка обеих платформ, установщик, обновление и содержимое артефактов. Доказательства привязаны к хешам проверенных артефактов.

Статусы: `не проверено`, `пройдено`, `не пройдено`, `не поддерживается`. Для «пройдено» требуется ссылка на тест/лог/снимок и точную сборку. Успех чистых JVM-тестов не переносится на native TUN, Windows WFP, Android VpnService или сетевой транспорт.

## Ограничение рабочего ноутбука

На ноутбуке пользователя запрещены запуск приложения или сетевого ядра для проверки, переключение VPN, изменение маршрутов, адаптеров, DNS и фильтров. Сетевые сценарии выполняются в отдельной Windows VM и на Android-эмуляторе/тестовом устройстве. Разрешены чтение исходников и метаданных, сборка, чистые тесты и распаковка проверенных файлов в указанную папку.

Начальный осмотр среды обнаружил `android-sdk/platform-tools/adb.exe`. В PATH нет `emulator`, QEMU, VirtualBox или VMware; SDK не содержит `emulator.exe`, пользовательская папка AVD не найдена, модуль Hyper-V не найден. Это ограниченный осмотр доступной среды, а не утверждение об отсутствии любой внешней тестовой машины. Без отдельного стенда сетевые критерии остаются непроверенными.

## Начальные подтверждения и блокеры

- Общий слой предыдущей реализации имеет 44 новых чистых теста. Их успешность описана в [ходе реализации](v1.1.0-progress.md); независимая приёмка native/runtime/UI на этом основании не пройдена.
- Закреплённое ядро `sing-box-lx 1.14.1-lx.8` и текущие оболочки закрывают прежний экземпляр при reload/start. Начальная capability — `RESTART_ONLY`. До нового проверенного механизма `TUN-02`, `APPLY-02` не выполнены.
- Начальный runtime не подключён к Expert UI; распакованная ранее версия 1.0.13 не выполняет основную задачу v1.1.0.
- Нельзя отмечать всю версию надёжной, если изолированный сетевой стенд не прогнал `TUN`, `DNS`, `COLD`, `CRASH` и `EXT` сценарии. Неизмеренная гарантия остаётся непроверенной в отчёте и интерфейсе.

## Матрица результатов

Для каждого ID сохраняется: платформа, хеш артефакта, revision, дата, команда/стенд, ожидаемый результат, наблюдение и ссылка на лог. Фикстуры сценариев для стенда размещаются в игнорируемой папке `build/v1.1.0-acceptance`; они используют только вымышленные адреса и не запускают сеть ноутбука.

Релиз готов, когда все основные gates выполнены на обеих платформах, открытых критических ошибок нет, неподдерживаемые дополнительные возможности обозначены правдиво и актуальный полный сценарий прошёл: импорт 1.0.x → прямой общий TUN → protected профиль/папка → отказ/восстановление → live-add/apply → холодный старт/сон → обновление без потери данных.

## Журнал независимой ревизии

Это найденные сценарии отказа, а не результаты их сетевого прогона. Статус исправления подтверждается отдельным регрессионным тестом и повторным просмотром.

| Ошибка | Наблюдение в исходниках | Требуемое подтверждение |
|---|---|---|
| MIG-01 | Старый именованный PROXY-родитель с дочерними условиями мигрировал в конечную Channel-цель, запрещённую новым валидатором для узла с детьми. Миграция уже изменена: структурный PROXY получает CurrentExit. | Валидный архив с именованным родителем, условным ребёнком и «иначе» проходит codec/import; исходный bundle остаётся равным прежнему. |
| RUN-01 | При смене сети очищаются samples, но старый выполняющийся probe может вернуть успех и снова записать его как свежий: его relevance проверяла только generation TUN. | Fake-clock/barrier тест: успешный старый probe завершился после NetworkChanged и не создал свежую оценку новой сети. |

## Независимая проверка нативного слоя

Тестовая Go-подмена `go -overlay` использует реальный `exitGate` из рабочей сборки; заглушка заменяет только поставщика выхода. Она не открывает TUN и не меняет сеть ноутбука. Это проверка конкурентного допуска потоков, а не доказательство работы пакетного стека или отсутствия утечек.

- 100 одновременных запросов, поровну TCP и UDP: один запуск поставщика, 100 ожидающих потоков, затем 100 активных, после закрытия — ноль. Проверено.
- Отмена ожидающего потока освобождает счётчик очереди. Проверено.
- Проверка спящего выхода не будит его и не меняет таймер пользовательской активности. Проверено.
- Полный предел первого потока сначала **не прошёл**: при допустимом бюджете 1000 мс `DialContext` продолжил ожидание более 1600 мс после допуска. После исправления повторный тест TCP и отдельный тест UDP завершились по сроку 1000 мс. Проверено.
- Закрытый выход сначала **не прошёл** проверку позднего завершения запуска: возврат из задержанного запуска менял `closed` на `failed`. После исправления поздний запуск сохраняет терминальное состояние. Проверено.
- Выбор быстрейшего выхода проверен целиком до возврата реального TCP-соединения: один кандидат отвечает HTTPS на локальном тестовом сервере, соседний зависает. Соединение установилось до истечения общего бюджета 1000 мс. Проверено.

Дополнительно проверены удержание ста старых потоков после публикации новой версии, закрытие обеих версий при явном Stop и отказ отменённой публикации без смены текущей версии. Восстановление действительно создаёт нового поставщика и закрывает прежние учитываемые TCP/UDP-соединения. Полный независимый набор из десяти Go-проверок прошёл. Доверие к сертификату локального HTTPS-сервера изменяется только внутри процесса теста; сертификаты Windows не устанавливаются.

Одиннадцатая проверка сначала **не прошла**: запрос TCP, уже ожидающий ответа прежнего поставщика, вернулся успешно после завершённого восстановления. После добавления ограждения по поколению транспортного выхода и отмены его контекста позднее соединение отвергается. Повторный запуск проверил исправление.

Двенадцатая проверка сначала **не прошла**: после успешного соединения контекст, переданный настоящим gate поставщику, уже отменён. После введения отключаемого срока подготовки и привязки освобождения к закрытию соединения установленный поток продолжает жить. Повторная проверка TCP/UDP сохраняет потоки дольше исходного бюджета и успешно записывает данные. Весь набор из двенадцати gate-проверок прошёл повторный независимый запуск.

Отдельная проверка настоящей очереди `udpNatConn` закреплённого sing-tun прошла: из тысячи датаграмм по 1500 и 65 535 байт удерживаются первые пакеты в FIFO-порядке, с максимумом 32 датаграммы и 256 КиБ; новые при переполнении отбрасываются. Чтение уменьшает фактический учёт байтов до нуля, закрытая очередь отвергает поздний пакет. Проверка настоящего локального gVisor-стека с тегом `with_gvisor` подтвердила TCP-буферы: по 32 КиБ по умолчанию и не более 128 КиБ на приём и передачу. Общий ingress допускает 512 потоков во всех выходах и удержанных версиях; следовательно, оценка этих TCP-буферов для допущенных потоков составляет 128 МиБ полезной нагрузки. Это не граница всей памяти процесса: объекты, SYN-очередь, буферы до допуска, транспортные буферы и UDP учитываются отдельно. Фактическая доставка через гостевой TUN требует отдельного подтверждения.

Дополнительная проверка устаревшего health-результата после замены транспорта обнаружила два разных момента публикации. Отменённая проверка прежнего транспорта уже не увеличивает число ошибок его замены — повторный тест прошёл. Затем успешный HTTPS-ответ, полученный до замены транспорта и опубликованный папкой после замены, мог стать свежей оценкой нового, непроверенного транспорта. Проверка с барьером на публикации сначала **не прошла**. После переноса проверки поколения под блокировку самой публикации и сохранения идентичности транспорта в оценке папки оба сценария прошли. Независимый повторный запуск рабочей Go-папки проверил все четырнадцать admission/health-сценариев и отдельное деление подключённых подсетей без открытия TUN. Фикстуры перенесены в `native/overlay/lernet/expert/stale_health_test.go`; исходная копия: `build/v1.1.0-acceptance/stale_health_acceptance_test.go`.

Тесты и конфигурация подмены: `build/v1.1.0-acceptance/native_gate_acceptance_test.go`, `udp_order_acceptance_test.go`, `go-overlay-gates.json`, `go-overlay-udp.json`. Gate-сценарии перенесены владельцем native в `native/overlay/lernet/expert/admission_test.go` и повторно запускались без подмены. Доставка TCP/UDP через TUN, закрытие старых потоков после Block, идентичность TUN и последствия сбоя ОС пока этими тестами не подтверждены.

Для изолированного Android-стенда в SDK проекта установлены официальный эмулятор 37.2.12 и образ Android 36 Google APIs x86_64. `emulator -accel-check` подтвердил доступный WHPX. AVD и временные файлы помещены в игнорируемую папку приёмки. Настройки Windows, установленный LerNET и сетевые маршруты ноутбука не менялись. Документация среды: [переменные эмулятора](https://developer.android.com/tools/variables), [ускорение виртуализации](https://developer.android.com/studio/run/emulator-acceleration).

Официальный образ Windows 11 Enterprise LTSC Evaluation получен по ссылке Microsoft, размер 5 112 850 432 байта, SHA256 `67cec5865eaa037a72ddc633a717a10a2bed50778862267223ddb9c60ef5da68`. Контрольная сумма фиксирует полученный образ; отдельная опубликованная Microsoft сумма не заявляется. ## Дополнительная ревизия переключения режимов и DNS

### Область защиты и определение домена

`ROUTE-03` и `DNS-01` проверяют запрет прямого fallback для фактически совпавшего защищённого пути. Они не доказывают распознавание любого сайта по имени. Закреплённый matcher возвращает несовпадение, если имя назначения отсутствует; TLS/QUIC sniffing читает доступное имя, а DNS reverse mapping хранит IP → имя с TTL и не устраняет общий IP нескольких сайтов. Собственный DoH приложения, ECH или обращение сразу к IP могут скрыть искомый домен. Предпросмотр при недостаточных данных должен показывать неопределённость. Прямой маршрут по умолчанию сохраняется; глобальный запрет неизвестных доменов не включён. Для строгого охвата применяются защита всего приложения с политикой неизвестного владельца, фактическая IP/подсеть или защищённый общий маршрут. [Пояснение для пользователя](v1.1.0-domain-identification.md).

`TUN`-критерии относятся к сетевым соединениям к внешним назначениям и поддерживаемым маршрутам LAN. Loopback/собственные адреса устройства не выдаются за перехваченный интернет-трафик. Отдельные контрольные и bootstrap-сокеты ядра разрешены для работы выходов и исключения петли; разрешение не передаётся совпавшему защищённому бизнес-соединению. Перехват LAN/IPv6 и точные исключения проверяются реальным гостевым трафиком, отдельно от компиляции схемы.

Windows проверяет полное покрытие действующих внешних префиксов собственными маршрутами и повторяет снимок через 2 секунды. Это обнаружение изменений, а не атомарный запрет ОС создать обходящий маршрут. При выключенной системной защите другой процесс может добавить более точный маршрут между снимками; отсутствие такого окна не заявляется. Для гарантии при обходе/исчезновении TUN нужна включённая и фактически подтверждённая защита WFP. Гостевой сценарий должен добавить чужой более точный маршрут после запуска и проверить отсутствие прямого трафика при активной защите; затем восстановить только изменения теста.

### Переключение режимов и системный DNS

Проверка MODE-02 обнаружила, что неудачный запуск Expert останавливал ранее работающий обычный VPN и не восстанавливал его. Для Windows добавлена одноразовая точка восстановления: фактически живой RUNNING-процесс, точный исполняемый файл и конфигурация, профиль, эффективный режим и поколение пользовательского намерения. Более поздние Stop, Connect, выбор профиля, смена режима или изменение сохранённых данных отменяют восстановление. Нормальный Stop Expert не включает прежний VPN автоматически. Восстановление также запрещено, пока остаётся системная защита Expert; её нельзя молча снимать ради запуска Simple.

В той же ревизии Windows выявлены два нарушения владения: Stop сообщал об остановке без подтверждения выхода процесса, а задержанный старт мог создать процесс после отмены. Создание процесса теперь ограждено общей блокировкой с Stop, неподтверждённое завершение сохраняет владение и запрещает новый TUN. Отдельные временные конфигурации исключают перезапись нового запуска задержанной проверкой прежнего. Добавлены десять чистых тестов в `WindowsSimpleRestorationTest`: модели намерения, заглушки процессов, отказ Simple при оставшейся/неизвестной системной защите и удаление секретов до записи в UI/журнал и обрезки строки. Они не запускают сетевое ядро. Результат их выполнения и фактическое восстановление в гостевой ОС фиксируются отдельно; наличие исходников не считается прохождением MODE-02.

Ревизия Android cleanup обнаружила потерю владения после ошибки JNI Close: закрытие оригинального дескриптора службой не доказывало завершения нативного дубликата, а повторный Close мог возвращать ложный успех. Исправленная схема удерживает нативный объект и резервирование до подтверждённого закрытия обоих владельцев. Ошибка Close остаётся неопределённым состоянием; только строгое фактическое `close_confirmed=true` либо успешное первоначальное закрытие разрешает освобождение. Повторный Stop не обещается как универсальное исправление; интерфейс должен объяснять принудительную остановку приложения и отдельные последствия Android lockdown. Чистые bridge-проверки и подтверждение на устройстве фиксируются отдельно.

Для Android подтверждено ограничение системного DNS: служба может отправлять запрос без имени исходного приложения. Ранний запрет неизвестного владельца делал защищённую DNS-проекцию недостижимой. Сгенерированное исключение теперь должно пропускать такие запросы только в проверенный префикс DNS-правил: защищённый выход, локальный ответ или завершающий запрет; обычные запросы неизвестного владельца не должны проваливаться в прямой DNS. Отдельная ошибка касалась явного Block без галочки защиты: неточная DNS-проекция пропускалась, хотя требовался запрет. Она также должна блокировать соответствующее разрешение имён. Если принадлежность системного DNS установить нельзя, запрет может затронуть больше приложений; интерфейс обязан явно объяснять это последствие. Приёмка DNS-01 всё ещё требует настоящего трафика гостевого Android и наблюдения underlay.

### Предварительный снимок и владение Windows

Перед включением Expert добавлен отдельный локальный снимок с ограничением чтения 8 секунд: свойства адаптеров, выбранные пути к двум числовым IPv4 и одному IPv6 адресу, подключённые профили встроенного VPN Windows. [Find-NetRoute](https://learn.microsoft.com/en-us/powershell/module/nettcpip/find-netroute?view=windowsserver2025-ps) читает выбранный путь; [Get-VpnConnection](https://learn.microsoft.com/en-us/powershell/module/vpnclient/get-vpnconnection?view=windowsserver2025-ps) читает телефонную книгу VPN. Сценарий не посылает проверочных пакетов и не меняет параметры сети. Имя адаптера не считается доказательством владельца: виртуальный путь может принадлежать текущему LerNET, другому VPN или виртуальной сети. Неполный снимок и неизвестный тип остаются явными предупреждениями. Полная консоль наблюдения доступна отдельно.

Чистые тесты предварительного снимка проверяют отсутствие вывода о VPN по похожему имени, раздельные факты виртуального маршрута и подключённого встроенного VPN, неизвестные свойства, таймаут, отмену и отсутствие содержимого неразобранного ответа в ошибках. Синтаксис постоянного PowerShell-сценария прошёл проверку AST без исполнения. Результат JVM-тестов и работа диалога фиксируются отдельным шагом.

Ревизия обнаружила отсутствие гарантии завершения экспертного процесса после принудительной смерти GUI. Наличие обработчика штатного завершения JVM недостаточно. Процесс из защищённой папки также может оказаться вне дерева уже завершённого установочного launcher. Нативный контроль должен получить отдельное подтверждённое владение жизнью GUI, а системные блокирующие фильтры должны сохраняться независимо от обоих процессов. Исправление и фактический сценарий убийства процесса в гостевой Windows ещё требуют подтверждения.

В изолированном Android подготовлены контрольные TCP/UDP echo-серверы, два SOCKS5 выхода с UDP relay и гостевой x86_64 генератор трафика. Они ограничены синтетическими loopback назначениями. Генератор собран NDK с `-Wall -Wextra -Werror`; серверы прошли проверку синтаксиса Python. Эти подготовительные шаги не являются подтверждением работы TUN, холодного запуска, редиректа или сохранения интерфейса после Apply.

При повторной ревизии Windows найдена гонка позднего отказа: завершившийся запрос старого процесса мог остановить уже созданный следующий процесс через общий указатель владельца. Теперь асинхронный запрос хранит конкретный объект процесса, клиент управления и поколение; очистка проверяет их под блокировкой до изменения состояния. Явный Stop по-прежнему отменяет текущую операцию заранее. Добавлены два барьерных loopback-сценария: поздний отказ Start после нового согласования возможностей и неопределённый Apply после запуска нового процесса. Они проверяют сохранение нового владельца, версии, поколения и резервирования Simple. Выполнение этих JVM-сценариев фиксируется отдельно; исходники тестов не считаются подтверждением TUN-02.

Дополнительно найден обход границы повышенных прав: прежний ACL разрешал чтение bearer-секрета владельцу файла, хотя повышенная и обычная копия одного аккаунта имеют одинаковый SID. Обычный процесс мог получить управление ядром, которому WFP разрешает внешний трафик. Новый секрет создаётся атомарно под уже защищённой папкой комплектного ядра; владелец — Administrators, защищённый DACL разрешает доступ только Administrators и SYSTEM. Оба объекта — каталог и файл — получают права при создании, затем проверяются обратным чтением. Это исключает промежуток между обычным созданием и исправлением ACL. Контракты создания сверены с [CreateDirectoryW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createdirectoryw) и [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew).

Пять чистых проверок прав/layout подготовлены в `WindowsControlSecretTest`. Отдельный гостевой helper сохраняет SID пользователя, переводит Administrators в deny-only и убирает повышенные привилегии через [CreateRestrictedToken](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-createrestrictedtoken); он требует реального ERROR_ACCESS_DENIED на чтение и WRITE_DAC файла и каталога. Фикстуры Java/Go в `build/v1.1.0-acceptance/control-secret-guest` скомпилированы; Windows helper SHA256 `c26f5739e106db4a79498abaac85a980a6aefab33d94b3089752c4d9d8b08af3`. На ноутбуке helper не запускался и ACL не менялись. Фактическое подтверждение в гостевой Windows остаётся обязательным.

Публикация RUNNING Windows теперь дополнительно ожидает подтверждения динамических разрешений Guardian для конкретного TUN. Эта проверка происходит под блокировкой владельца до сохранения идентичности и запуска наблюдения; явный Stop заранее меняет поколение намерения. В `WindowsExpertBackendTest` подготовлены ещё два барьерных сценария: отказ разрешения не публикует активную схему и завершает свой процесс; Stop во время проверки отменяет публикацию, после чего новый владелец получает собственное разрешение без позднего снятия защиты старым запросом. Всего в классе 11 чистых сценариев. Фактические фильтры WFP этим классом не создаются; результат JVM-проверок и реальное прохождение гостевой Windows фиксируются отдельно.
