# LerNET v1.0.10 — консоль наблюдения за сетью

Статус: расширенный план после замечания о недостаточной глубине Windows-анализа, 30 сентября 2026. База реализации: v1.0.9, коммит `aa5ddcf`. Этот документ — основная спецификация первого шага к v1.1.0. Версия приложения пока не меняется; реализация и выпуск выполняются следующим этапом.

## Результат

Пользователь открывает «Сеть устройства» без подключения LerNET и видит, какие интерфейсы, маршруты, настройки DNS/прокси и сетевые компоненты участвуют в работе устройства. Консоль объясняет наблюдаемые препятствия для выбранного режима LerNET, позволяет сравнить два локальных снимка и на Windows разобрать конкретный сбой по событиям ОС и короткой диагностической записи. Проблема: сторонний VPN мог оставить настройки, но доступность сервера не объясняет, куда реально идёт трафик устройства и на каком этапе обрывается соединение.

На Windows это отдельное окно внутри LerNET с собственным состоянием сбора; на Android — отдельный экран. Предположение: отдельный установщик/EXE для анализатора не нужен. Закрытие окна не отключает VPN. Открытие окна не создаёт новый DesktopController, не запускает ядро и не запрашивает VpnService-разрешение.

## Интерфейс

Сверху: время снимка, доступные права, состояние сбора и краткое объяснение текущего выхода. Ниже вкладки:

1. **Обзор:** доступные сети, IPv4/IPv6, текущие направления выхода, статус внешнего IP, найденные проблемы.
2. **Приложения и каналы:** VPN-профили, процессы/службы, виртуальные адаптеры. «Установлено», «запущен процесс», «интерфейс поднят», «маршрут выбран» — разные состояния. Один компонент может быть связан с несколькими приложениями; не делать ложное объединение по названию.
3. **Маршруты:** таблица и проверка выбранного назначения, шлюз, интерфейс, префикс, метрики, IPv4/IPv6, активный/постоянный маршрут, сетевой compartment.
4. **DNS и прокси:** серверы DNS по интерфейсам, DNS-политики по доменам, статические записи hosts, настройки пользовательского прокси и WinHTTP, PAC/WPAD как конфигурация.
5. **Фильтры:** правила Windows Firewall, доступные WFP-провайдеры/фильтры, драйверы и привязки компонентов к адаптерам. Для непрозрачного callout показывается отсутствие подробностей, а не выдуманная причина блокировки.
6. **Изменения:** два выбранных снимка, появившиеся/исчезнувшие адаптеры и маршруты, изменившиеся DNS/прокси/фильтры. Изменение после запуска приложения не доказывает, что именно оно автор настройки.

Частые действия: «Обновить», «Проверить конфликт», «Сравнить снимки», «Разобрать сбой». Подробные поля раскрываются из карточки. «Сохранить отчёт» явно сохраняет локальный файл; отправка куда-либо не выполняется. Windows-разбор сбоя открывает последовательность событий выбранной попытки, связанные процессы, фильтры и компоненты. Начальный экран остаётся кратким; подробности системы и техническая запись доступны по раскрытию.

Большая часть основных полей доступна без повышения прав. Администратор расширяет доступ к защищённым процессам, системным настройкам и фильтрам; доступ всё равно проверяется для каждого источника. Отказ чтения, отсутствие компонента, таймаут, устаревший снимок и пустой результат имеют разные статусы.

Снимок включает версию ОС, контекст пользователя/профиля и время начала/окончания сбора. Повышение прав через другую учётную запись не должно незаметно подменять пользовательские proxy/VPN-настройки: показывать, для какого SID они прочитаны и какие сведения исходного пользователя недоступны. Снимок не атомарный; изменение сети во время сбора помечается. Для сравнения интерфейсов использовать GUID/LUID и контекст, а не только изменяемый ifIndex.

### Связь с приложением и протоколом

У каждой связи «приложение → компонент» должны быть основание и степень уверенности: точный PID владельца сокета; путь службы; сведения драйвера; WFP provider GUID; несекретная системная VPN-запись; либо только совпадение названия. Общий драйвер Wintun/TAP не идентифицирует единственного клиента. У стороннего VPN Windows может быть виден адаптер/процесс и зашифрованное соединение, но не внутренний протокол и конфигурация. В этом случае пишем «ОС не раскрывает», не угадываем протокол по порту 443.

Подписанный издатель подтверждает подпись/идентичность соответствующего файла, но не доказывает отсутствие конфликта или авторство конкретного маршрута. Установленная программа без наблюдаемого сетевого влияния — информация, не предупреждение.

## Правила выявления конфликтов

Разделить **факт**, **потенциальный конфликт** и **недостаточно данных**. Каждое сообщение содержит код, источник, время, затронутый объект, ожидаемое поведение и объяснение. Отдельно показывать уверенность связи с приложением; она не равна серьёзности проблемы.

- Для полного VPN нет административных прав: объяснить ограничение режима; для прокси это не ошибка.
- Нужный локальный порт занят другим PID: показать адрес/семейство/порт/владельца. Учитывать собственный работающий процесс LerNET и не считать его чужим конфликтом.
- Сторонний туннель имеет более специфичные маршруты для соответствующих назначений: показать конкретные префиксы и следующий интерфейс. Корпоративный split tunnel сам по себе не мешает остальному трафику.
- Путь к VPN-серверу выбирает сторонний туннель или неработающий интерфейс: факт выбора маршрута, возможность зависимости одного туннеля от другого. Фактическая доступность требует отдельной сетевой проверки.
- После отключения приложения остаётся статический прокси/DNS на loopback, но подходящего listener в снимке нет: возможная неработающая настройка; не назначать авторство по соседству во времени.
- Сохранённый маршрут выбирает отключённый адаптер, пересекаются локальные/корпоративные/TUN-подсети, IPv4 и IPv6 выбирают разные пути: показать объекты и последствия для конкретного назначения. В IPv6 не обещать защиту только по успешной проверке IPv4.
- Явная подходящая блокировка firewall/WFP: показать найденное правило и известные условия. Неполное чтение политики или непрозрачный callout ограничивает заключение.

До подключения анализ показывает факты текущего состояния и риски планируемого подключения. Таблица будущих маршрутов и динамические решения драйверов ещё не существуют; «будет мешать» не представляется гарантией. После подключения по действию пользователя снимок можно сравнить с предыдущим. Отсутствие найденных конфликтов означает именно это, а не «подключение гарантированно работает».

Проверка пути учитывает выбранный режим и назначения из конфигурации LerNET. Трафик, который пользователь намеренно отправляет напрямую/в корпоративную сеть, нельзя объявлять утечкой только потому, что интерфейс отличается от LerNET. Существующая проверка URL туннеля остаётся отдельной проверкой здоровья.

## Локальный анализ и внешние измерения

По умолчанию новая консоль полностью пассивна: чтение ОС и локальных баз, без HTTP, DNS-запросов, traceroute, получения PAC/WPAD или запуска VPN. Проверка маршрута принимает IP-литерал; имя домена без готового результата не разрешается автоматически. PAC отображается как настройка, не загружается и не исполняется в пассивном режиме.

Публичный IP за NAT/CGNAT нельзя надёжно узнать из одного локального адреса интерфейса. Для этого необходим внешний наблюдатель. Поэтому «Проверить внешний IP» — отдельное действие с видимым сервисом назначения и указанием измеренного пути (обычный маршрут устройства или явно выбранный прокси). Сервис неизбежно видит исходящий IP, даже когда отчёт и настройки ему не отправляются. Подключение/обрыв VPN не запускает проверку автоматически. Обход активного VPN для выяснения исходного IP не выполняется автоматически.

Страна для уже известного IP определяется существующей LocalGeoIp локально и показывается как оценка с версией базы. ASN/организация требуют новой локальной базы с проверкой лицензии и датой обновления; текущий RipeStatHopDetails отправляет запрашиваемый IP в RIPE и не подходит для пассивного режима. До появления локальной базы ASN показывать отсутствие сведений. ASN/организация сети выхода не всегда равны провайдеру домашнего доступа, особенно при VPN/прокси/корпоративном шлюзе.

Снимки находятся в памяти до явного локального сохранения. Экспорт включает схемную версию и предупреждение о наличии IP, путей/названий приложений и корпоративных доменов. Пароли VPN, PSK, токены и приватные ключи не собираются. Анализируемые данные не используются как команды или пути исполняемых файлов.

## Дополнительная глубина Windows

Пассивная инвентаризация — один из трёх уровней. Для локализации реального сбоя нужны также **история доступных событий** и **короткая диагностическая сессия**. Права администратора позволяют пользоваться встроенными средствами Windows, а не только опрашивать конфигурацию.

### История и разбор событий

- Читать ограниченный интервал имеющихся журналов: сетевой адаптер/драйвер, TCP/IP, DHCP, DNS Client, WLAN-AutoConfig, RasClient/RasMan, IKEEXT, Schannel и Security/WFP в пределах доступности. Набор каналов, включение и поля зависят от ОС. Само наличие имени канала не означает, что события записывались.
- Событие WFP 5157 при настроенном аудите содержит процесс, адреса/порты и runtime ID блокирующего фильтра. Связать ID с доступным снимком WFP и его provider/условиями. Если фильтр уже исчез или ID относится к другой загрузке/сессии ОС, показывать невозможность сопоставления, а не подбирать совпадение по одному номеру.
- Построить временную шкалу: смена Wi-Fi/интерфейса → новый адрес/шлюз → DNS-ошибка → попытка TCP → блокировка/сброс → завершение ядра. Причинную связь показывать только при общем назначении/потоке/процессе и достаточных данных; события рядом во времени остаются корреляцией.
- Читать существующий журнал LerNET вместе с событиями ОС, не смешивая отказ запуска ядра, отказ создания TUN и таймаут передачи через уже работающий туннель.
- Если системный аудит/канал отключён, объяснить отсутствие истории. Не обещать восстановление прошлого по будущему включению записи и не менять системную политику аудита автоматически.

### Короткая запись поведения

Действие «Разобрать сбой» предлагает выбрать приложение/профиль/адрес и запустить запись, затем воспроизвести проблему. Для собственной проверки LerNET известны отдельные этапы DNS, TCP, TLS, HTTP и создание TUN. Для сторонних процессов используются доступные ETW/packet события; отсутствие стадии в записи не означает, что стадия не выполнялась. Schannel не покрывает TLS всех программ: у браузеров и других приложений бывают собственные библиотеки.

- **ETW / netsh trace:** события сетевого стека и выбранных провайдеров; сопоставление PID, endpoints, времени и ошибок. Поддерживаемые схемы событий проверять по версии Windows; неизвестные события сохранять как необработанные метаданные с причиной, не ошибочную интерпретацию.
- **Pktmon:** доступные места прохождения пакета внутри сетевого стека, счётчики и локальные drop reasons, например несоответствие MTU. Не обещать покрытие каждого стороннего драйвера; не считать несколько наблюдений одного пакета в разных компонентах ретрансляциями.
- **WFP:** доступные netevents/capture и связанные фильтры для конкретного трафика. Отдельно от списка Firewall rules: сторонняя фильтрация может выполняться callout-драйвером. Запись фиксирует наблюдаемые решения, а статическая таблица даёт контекст.
- **TCP:** подтверждённые события подключения/закрытия; SYN без наблюдаемого ответа, повторные отправки, RST, измеренная задержка. «Ответ не наблюдался» не определяет виновника вне устройства. Источник RST/ICMP в пакете не доказывает физического отправителя.
- **Туннель и внешний транспорт:** показывать внутренний поток приложения и внешний поток VPN как разные объекты. Если VPN шифрует/объединяет потоки, соответствие одного внешнего пакета конкретному внутреннему соединению может быть неизвестно. Не обещать расшифровку TLS или чужой конфигурации.

По умолчанию запись ограничена выбранным сценарием, 30–60 секундами, локальным кольцевым буфером и бюджетом диска. Начать с ETW/WFP метаданных и счётчиков; захват фрагментов пакетов включается явно с указанием границ и содержимого. Усечение до заголовков не считать гарантией отсутствия пользовательских данных при вложенных/переменных заголовках. Полная запись пакетов не включена по умолчанию.

Диагностическая сессия не меняет маршруты, DNS, MTU или фильтрацию, но создаёт временную запись/подписки и расходует ресурсы. Перед стартом проверять capabilities и состояние чужих трассировок. Не сбрасывать чужие pktmon counters/filters, не останавливать глобальную чужую запись и не включать WFP netevents/audit policy молча. Если инструмент не допускает независимую сессию или без изменения глобальных настроек не работает — источник недоступен для данного запуска с объяснением. Останавливать только доказанно собственную сессию; предусмотреть отмену, завершение по лимиту и уборку собственной записи после аварии.

| Wi-Fi/локальная сеть | Доступные signal/channel/band, link speed, roaming/disconnect events, сведения соседей из существующей ARP/ND cache, доступность шлюза по явному тесту | Выявлять смену сети или проблемы до туннеля. Не запускать поиск соседей или сканирование LAN автоматически. Данные WLAN могут требовать разрешения на местоположение даже на Windows. |
| TLS собственной проверки | Этап и код отказа, цепочка публичных сертификатов, имя сервера, срок/доверие, согласованные параметры; доступные Schannel events | Отличать отказ сертификата/рукопожатия от общего timeout. Корпоративный корневой сертификат — контекст; сам по себе он не доказывает перехват. Приватные ключи не собираются. |

### Проверки по явному действию

К диагностической записи можно привязать целевые тесты: разрешение имени через выбранный DNS, TCP connect на нужный порт, TLS handshake и HTTP запрос с раздельными таймингами; проверка шлюза, сравнение IPv4/IPv6, проверка поддерживаемого path MTU. Отказ ICMP не доказывает недоступность TCP и не даёт автоматически измеренный MTU. Источник/маршрут каждого теста указывать в результате. Выход напрямую в обход активного VPN не используется автоматически.

Пример итогового заключения при наличии доказательств: «Процесс LerNET попытался открыть TCP к адресу X. ОС зарегистрировала WFP 5157 с фильтром Y. Снимок фильтра Y содержит provider Z и такие-то условия». Имя TampleVPN появляется только если связь provider/службы/файла подтверждена. Если пакеты вышли в физический интерфейс, а ответа в доступной записи нет, заключение остаётся «нет наблюдаемого ответа за пределами устройства», без утверждения о блокировке провайдером.

## Android

Общий формат снимка и сообщений сохраняется, но набор источников ограничен обычными Android API. Доступные сети, transport/capabilities, LinkProperties, адреса, DNS, маршруты и MTU показываются в пределах доступности для UID LerNET; это не полная инвентаризация всей ОС. Запрашивать только наблюдение, не новый VPN-туннель ради диагностики.

Собственный VPN и его параметры известны LerNET. Чужой VPN может быть виден как transport VPN, но его UID/имя и конфигурация обычно скрыты. NetworkCapabilities.getOwnerUid раскрывается владельцу сети; права Windows администратора не имеют аналога для обычного Android приложения. Не требовать root/device owner для первой версии. Недоступные поля подписывать причиной, не подставлять имя из списка установленных приложений.

Для текущего пользователя/профиля активен один VpnService; при запуске нового возможно замещение существующего. Другой рабочий профиль — другой контекст. Список видимых приложений с VPN-сервисом означает кандидатов, а не доказательство активного владельца. Проверка always-on/lockdown показывает собственное доступное состояние; чужие ограничения обозначаются недоступными, если ОС их не раскрывает.

## Реализация по шагам

### 1. Локальный снимок и окно, доступное без VPN

- В `core-engine-shared/src/main/kotlin/app/lernet/engine/net/observation/` добавить небольшие DTO снимка, статусы источников, ссылки на доказательства и чистые функции анализа/сравнения. Нативный сбор не помещать в общий модуль.
- Windows: новые `WindowsNetworkObservation` и `DesktopNetworkObservationController` рядом с существующим WindowsTunnelHealth. Один фиксированный сбор PowerShell/CIM с явным allowlist полей и UTF-8 JSON для интерфейсов, маршрутов, DNS, proxy, listeners, native VPN profiles; IP Helper для выбора маршрута. Отдельные ошибки источников, отмена и ограниченное ожидание, без `Format-List`/парсинга локализованного текста.
- Использовать `WindowsAppCatalog` для понятных имён кандидатов и `WindowsProcessIdentity` для иконок; точную принадлежность получать из PID/служб/драйверов, а не из эвристики каталога установленных программ.
- `desktop-app/.../Main.kt`: отдельное окно «Сеть устройства»; его жизненный цикл не создаёт/закрывает контроллер подключения. Обновлять по кнопке; лёгкие уведомления ОС о смене интерфейса/маршрута объединять, тяжёлый сбор запускать только при необходимости.
- Android: новый экран и collector поверх ConnectivityManager/LinkProperties. `app/.../vpn/DefaultNetworkMonitor.kt` остаётся монитором underlay для движка; для просмотра чужой сети не менять его listener и не вызывать requestNetwork, которое может влиять на выбор сети.

### 2. Анализ выбранного подключения и системных фильтров

- Чистые правила preflight используют снимок и ожидаемое подключение LerNET: режим, endpoint, требуемые порты, подсети и известные направления правил.
- Добавить доступное перечисление Windows Firewall/WFP и adapter bindings; отображать доступность/частичность. Не включать аудит ОС и не устанавливать драйвер/фильтры для сбора.
- После подтверждения анализа на снимках подключить его к `DesktopController.connectInternal` и Android старту без вызова `connect` для проверки. В первой версии предупреждение показывает основания и позволяет пользователю продолжить; известную ошибку запуска, например недостаток прав, объясняет существующий механизм режима/повышения прав.
- Показывать diff локальных снимков. Связь события со сторонним приложением остаётся предположением, если точного доказательства нет.

### 3. Разбор сбоя на Windows

- Добавить `WindowsNetworkEventReader` и `WindowsDiagnosticSession` в desktop observation package. Первый читает существующие события; второй управляет короткой записью через проверенные возможности ОС. Общий модуль получает нормализованные события и чистую функцию корреляции, не Windows-specific ETW структуры.
- Первый законченный сценарий v1.0.10: выбрать профиль/endpoint, начать запись, воспроизвести попытку, получить этап отказа, подходящие WFP события и контекст выбранного маршрута. Этот сценарий входит в целевой выпуск наряду с локальным снимком; новый драйвер или Npcap для него не требуется.
- Проверить наличие/версию штатных инструментов из системного каталога, доступность провайдеров, занятость сессий и права. Не запускать executable из произвольного PATH/отчёта. Способ вызова/аргументы фиксированные, назначения передаются как проверенные значения.
- Читать расширенные источники инвентаризации независимо. Winsock/NDIS/Hyper-V/IPsec/WLAN ошибки отображаются в соответствующем подразделе.
- UI: время записи, цель, предел объёма, остановка, временная шкала, доказательства и границы наблюдения. Запуск ядра/соединения — отдельное обычное действие пользователя, не побочный эффект кнопки записи.

### 4. Явные внешние измерения и локальный отчёт

- Отдельная кнопка внешнего IP, раздельные результаты IPv4/IPv6, путь/сервис/время/ошибка и отсутствие автоматического обхода VPN. Отмена/таймаут не переводят измерение в «VPN выключен».
- Повторно использовать LocalGeoIp; предусмотреть локальный ASN lookup после решения о базе и лицензии. Базы обновляются отдельным явным действием.
- Локальный JSON-отчёт со схемой и человекочитаемое представление. Отчёт не импортируется как `.lernet.json` конфигурация маршрутов. Не включать отчёты в репозиторий и регулярный журнал подключения.

## Проверка и критерии готовности

| Сценарий | Ожидаемый результат |
| --- | --- |
| Открытие/закрытие окна при активном LerNET | Не запускает/останавливает ядро, не переподключает VPN, не создаёт второй контроллер. |
| Пассивный снимок без интернета | Все доступные локальные разделы работают; в подставном сетевом клиенте ноль вызовов HTTP/DNS. Не вызываются методы изменения сети. |
| Нет прав/источник недоступен/долгий collector | Частичный снимок с конкретными причинами и временем; UI не зависает; пустые сведения не становятся статусом «VPN отсутствует». |
| Два `/1` стороннего туннеля и `/0` LerNET | Правило учитывает длину префикса; показывает конкретный выбранный интерфейс/риск, не только метрику `/0`. |
| Корпоративный split tunnel и виртуальный адаптер WSL | Корпоративные назначения объясняются; наличие WSL не отмечается как конфликт VPN. |
| Порт LerNET занят чужим/своим PID | Разные сообщения, правильный владелец; PID идентифицируется вместе со временем запуска. |
| IPv4 через TUN, IPv6 через иной интерфейс | Два результата и основания; не общее зелёное «всё защищено». |
| Сторонний процесс без протокола/общий Wintun | Нет выдуманного протокола и безусловного владельца адаптера. |
| Смена DNS/прокси между снимками | Diff содержит старое/новое значение и контекст; не назначает автора без доказательства. |
| Android: чужой VPN, own VPN, work profile, недоступный UID | Нет автоматического замещения VPN ради диагностики; принадлежность показана только при доступных доказательствах. |
| Явная проверка IP | Известны адрес сервиса и путь; отчёт/локальная инвентаризация не передаются; измерение не выходит напрямую ради обнаружения исходного IP. |
| WFP 5157 с подходящим фильтром/исчезнувшим фильтром | В первом случае основание и provider, во втором — факт блокировки без выдуманной идентификации. Учитывается загрузка ОС и время. |
| ETW provider недоступен/отключён системный аудит | Доступные источники работают; отсутствие событий не означает отсутствие сбоя. |
| Pktmon показывает пакет в трёх компонентах и один drop | Один пакет, отдельное местоположение потери; не три отправки или две ретрансляции. |
| Уже работает чужая трассировка | Она не прекращается/сбрасывается. Несовместимый источник помечается недоступным. |
| Отмена, лимит записи, аварийное завершение | Освобождена собственная сессия, лимит соблюдён; чужие настройки и сессии не изменены. |
| SYN без ответа/RST/TLS error | Разные заключения; локальная запись не назначает виновника за пределами устройства. |

Тесты общего анализа — в `:core-engine-shared:test`; Windows collector parsers/rules — отдельные unit tests в `:desktop-app:test --tests 'app.lernet.desktop.observation.*'`; Android collector с подставной ConnectivityManager-границей — `:app:testDebugUnitTest --tests 'app.lernet.ui.network.*'`. Эти классы планируются и ещё не существуют. Компиляция — `:app:compileDebugKotlin :desktop-app:compileKotlin` с in-process Kotlin, без запуска приложения.

Проверку реальных источников и конфликтов проводить на отдельном устройстве/VM со снимками: чистая Windows, native VPN, сторонний full tunnel, корпоративный split tunnel, выключенный VPN с сохранившимся proxy, обычные и административные права. На текущем ноутбуке приложение/VPN не запускать и не перезапускать. Нельзя заявить готовность детектора всех конфликтов только по unit tests.

## Границы и восстановление

v1.0.10 наблюдает и объясняет; управление несколькими туннелями, изменение правил сторонних VPN, автоматическая очистка сети и постоянный TUN относятся к следующим этапам. Нет миграции сохранённых профилей. Пассивные коллекторы только читают. Диагностическая запись создаёт собственные временные сессии/файлы; целевые тесты отправляют явно выбранные сетевые запросы. Закрытие окна отменяет сбор и освобождает собственные подписки/сессии. Выключение функции не требует отката маршрутов/DNS/фильтрации. Права администратора не дают гарантированного чтения внутреннего состояния любого стороннего драйвера или расшифровки любого трафика.

## Реализованный срез 1.0.10

В исходниках реализована самостоятельная «Сеть устройства»: отдельное окно Windows и экран Android с интерактивной схемой настроек, раскрываемыми источниками и доказательствами, поиском, сравнением двух снимков, локальным экспортом и отключаемым движением. В Windows доступен расчёт маршрута для числового IP, включая IPv6, метрики и сетевой контекст. Выбранный профиль LerNET добавляет пояснение пути к серверу и потенциальных зависимостей от виртуального адаптера; исходная конфигурация и ключи в отчёт не копируются.

Windows читает перечисленные в `WindowsNetworkObservation.definitions` фиксированные источники. Ограничения выборок и ошибки сохраняются отдельно; отсутствие данных или усечённая выборка не превращаются в утверждение «настройки удалены». Открытие/обновление консоли не отправляет сетевые пробы, не включает VPN и не меняет политики. Иконки программ загружаются только с проверенного локального диска без сетевых путей и reparse-переходов.

Короткая запись реализована через собственную UUID-сессию ETW с источником Microsoft-Windows-TCPIP, ограничением 45 секунд и круговым файлом 32 МБ. Принадлежность и фактический путь проверяются через CIM; отмена во время создания сверяет и завершает только эту сессию. Чужой pktmon/netsh trace не изменяется. Читаются существующие журналы и метаданные собственного ETL. Это запись системных событий; точечная трассировка выбранной программы, разбор сбросов pktmon, отдельные DNS/TCP/TLS/HTTP-пробы и автоматическое доказательное сопоставление WFP-фильтра историческому событию остаются отдельными следующими этапами. UI не обещает их наличие.

Внешний IP запрашивается только после подтверждения пользователем у api.ipify.org. Страна берётся из локальной базы. Ни инвентаризация, ни отчёт сервису не передаются. Провайдер без локального ASN-справочника не выдумывается. Android не раскрывает владельца чужого VPN по эвристике и не запускает VpnService ради наблюдения.

Проверка на ноутбуке ограничена компиляцией, чистыми тестами/подставным исполнителем и отдельной отрисовкой Compose на тестовых снимках. Настоящие сборщики Windows, ETW-сессия, приложение LerNET и VPN здесь не запускались. Интеграционная проверка доступности CIM/ETW и версии команд Windows требуется на отдельном устройстве или VM перед признанием этих источников проверенными в работе.


Ревью от 30 сентября 2026: исправления вызовов API, неполных/устаревающих данных и отмены описаны в [отчёте](../network-observation-1.0.10-review.md). Ограничение записи 45 секунд обеспечивается таймером работающего приложения; остановка по `-rf` после аварийного завершения не подтверждена интеграционным тестом.
